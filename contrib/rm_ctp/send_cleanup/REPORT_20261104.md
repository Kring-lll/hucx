# RM+CTP可靠SEND阶段汇报（2026-11-04）

## 先说目前结论

祝博，目前SEND已经把大小消息分段、保序去重、累计ACK、软件超时重传和有界失败退出串起来了。
正常MPI、集合通信和软件丢DATA/ACK、重复注入都取得了节点证据。之后恢复了小消息inline，复用了已有操作池，

性能上，小规模8B点对点已经接近RC；8B Alltoall仍明显慢于RC。共享Jetty的资源优势还在。
最近正式性能来自精简前的bdc记录池版本；最新a68精简版只做功能回归，没有重新测性能，不能混成同一批结果。

## 为什么加了可靠性后慢了，做过哪些改进

原iface_v2没有这套软件DATA重放和累计ACK。可靠模式额外保存可重放副本、管理序号和窗口、接收校验、
生成和处理ACK、回收在途记录，并在worker progress里扫描。inline只减少设备读取本地短报文的成本，
不会把这些工作消掉。RC也有可靠性开销，但更多由底层可靠连接承担，不能说RC不需要ACK。

已证实的诊断现象：在原a2b诊断窗口，PPN4 alltoall记录88069个接收DATA与88058次ACK分配，
ACK接近一DATA一份；发送元数据分配176127次，RX补充调用67923次。RC同期RX批量为16，可靠RM约2.59/次，
旧iface_v2约6.25/次。可见ACK及完成/RX补充是额外工作量来源，不能把所有延迟差都归给报头变大。
这些是不同模式各自诊断窗口的计数，不能把次数直接当OSU每次调用的包数。

节点perf采样不可用；scope插桩使alltoall可靠模式从未插桩约7μs变到22.68μs，扰动明显。
嵌套scope时间不能相加，也不能给出“0.5μs有多少纳秒归ACK”的精确账单。

已做两项单点改进：

1. 按完整WR长度决定inline。8B应用消息实际WR123B≤设备128B，已恢复inline。a2b同批对照点对点中位2.73→2.60μs；alltoall7.01→6.96μs，不能说inline解决了集合问题。
2. 重放元数据从逐次堆分配改为复用现有pending_mp；不另造内存池，TX数据副本仍来自原tx.mp。bdc同批点对点2.59→2.54μs，alltoall中位6.95→6.37μs，同时保留30.13μs长耗时样本。

用户决定暂不继续性能优化；这次精简只整理重复职责，没有改ACK策略或承诺性能提升。

## SEND分片与重传分别怎么做

MPI的大消息先由现有UCP eager/AM rendezvous路径按UCT上报能力拆成多条AM；RM没有再造一套MPI消息分片/重组协议。
每条AM交给RM可靠SEND后加软件头，成为一条≤4096B的URMA SEND；接收端RM先确认连续序号，
再交给现有UCP按消息ID/offset等机制重组。软件PSN编号的是这条SEND，不是网卡内部物理包。

4KiB减3B UB头再减104B可靠DATA头，AM_BCOPY可用3989B。SHORT接口自己的8B header也占这3989B，
所以不能让上层继续按旧4093B能力分片。eager不同协议还占自己的UCP头，应用边界不能直接等同3989B。

### 发送、接收和确认

- 同一本地iface到同一远端iface（含实例身份）为一条逻辑流，多个业务EP共用peer的发送PSN、接收期望PSN和窗口。
  不同进程地址空间各自独立；不同远端peer独立计数。同一iface共享Jetty不等于所有进程共享一个全局PSN计数器。
- 成功接受一条新SEND才推进tx_next；资源不足返回NO_RESOURCE，由已有pending重试，不浪费一个新序号。
- 发送端把完整软件报文保留在注册缓冲中，并放入重放队列。inline发送仍保留这个副本，供将来重传。
- 接收端只交付psn==rx_next。收到更大的PSN先丢弃，收到重复的也丢弃，不重复调用UCP；当前没有乱序缓存。
- 接收后标记ACK待发送；确认相应RX WQE补回后再允许累计ACK发出。ACK=N表示连续收到了N，不表示下一条一定丢了。
- ACK仅确认并清理已确认范围，不是立即要求从N+1重发。发送端未确认条目满足重传条件才再提交。

例子：期望101，101丢了，102到达后被丢弃并回复ACK100。发送端可能已发到102甚至窗口内更后面；
ACK100不会自动判定101丢失。101未确认、其本地CQE结束、达到RTO并有资源时，以原PSN重发；102也要之后补回。
这是按连续前缀确认、超前丢弃后补齐的保守方案，不是带选择ACK和乱序缓存的协议。

### 定时和错误出口

默认`SEND_RTO=100ms`、`SEND_RETRIES=256`、`SEND_TIMEOUT=30s`，固定间隔，尚未实现指数退避。
计时在worker progress里检查，无独立重传线程；每次progress控制/重发预算8。未确认且不在设备在途中的条目才可重发，
重发沿用原PSN及窗口占用，不再次扣窗口。次数限制或自接受后的绝对期限先到者触发失败。
资源不足要留出控制通道的SQ/CQ空间；provider提交终态错误或失败CQE走共享iface失败，不能承诺故障Jetty可恢复。

UM给了发送窗口、PSN、累计ACK和重传的参考。UM用16位PSN及模比较、EP状态、定时器退避和ACK请求/搭载等成熟机制；
RM当前64位不回绕、PSN放共享peer、固定RTO，不是直接复制UM。64位是实现取舍，减少回绕处理，但增大了软件头，并非RM硬件规定。

### 为什么远端ACK之后还要等本地CQE

远端ACK说明对端软件已按序接收；本地CQE决定最后一次设备提交何时不再访问本地缓冲。
ACK可能先于本地CQE到达，也可能丢ACK触发重发后旧ACK才到；不能只凭远端确认释放设备仍可能使用的缓冲。
正常DATA记录要同时满足远端确认和本地无在途；不确定提交的缓冲隔离到Jetty删除后处理。
这保护DMA缓冲生命周期，不是为了延迟上层交付。共享流中销毁一个EP也不能挖掉它已经占用的PSN。

## 报头有多大，为什么这么大

以下是软件提交给URMA的字节，不包含URMA/CTP/链路硬件报头。内存中的replay结构体也不算报头。

| 模式/报文 | 软件传输头 | 说明 |
|---|---:|---|
| RC普通AM | 3B | ub.am_id 1B＋ep_id 2B；上层UCP头及SHORT的8B header另算 |
| 原RM普通AM | 3B | 复用UB AM格式；独立流控控制报文另算 |
| UM普通AM | 8B | packet_type 4B（含类型/寻址位）、psn 2B、ack_psn 2B；不是3+8B，其他控制扩展另算 |
| 可靠RM DATA | 107B | 外层UB3B＋公共前缀36B＋返回地址68B |
| 可靠RM ACK | 39B | 外层UB3B＋公共前缀36B，无DATA返回地址 |

内层偏移从UB3B之后开始：

| 内层偏移 | 字节 | 字段 | 用途 |
|---|---:|---|---|
| 0～3 | 4 | magic | 区分本软件协议 |
| 4 | 1 | version | 当前版本3 |
| 5 | 1 | kind | DATA或ACK |
| 6 | 1 | AM-ID | 交给正确UCP回调；ACK为0 |
| 7 | 1 | reserved | 当前置0并校验，不称功能必需 |
| 8～15 | 8 | source instance | 识别对端iface生命周期 |
| 16～23 | 8 | destination instance | 防旧实例报文确认当前流 |
| 24～31 | 8 | PSN/累计ACK | DATA为本条序号，ACK为连续确认序号 |
| 32～35 | 4 | payload length | 长度一致性检查；ACK为0 |
| 36～51 | 16 | 返回EID | 让接收方知道回信目标设备身份 |
| 52～55 | 4 | 返回UASID | 地址空间/目标导入参数 |
| 56～103 | 48 | 返回iface地址 | 复用现有地址格式，见下表 |

最后48B地址块：

| 块内偏移 | 字节 | 字段 |
|---|---:|---|
| 0～7 | 8 | segment_va |
| 8～15 | 8 | segment_length |
| 16～19 | 4 | jetty_id |
| 20～23 | 4 | segment_flags |
| 24～27 | 4 | segment_token |
| 28 | 1 | address version |
| 29 | 1 | mode |
| 30～31 | 2 | address flags |
| 32～35 | 4 | rx_depth |
| 36～37 | 2 | max_peers |
| 38～39 | 2 | initial_credit |
| 40～47 | 8 | instance |

返回地址每条DATA都带，是为了无反向业务EP也能回ACK，且第一条DATA丢失时后续重传仍可建立返回目标。
这个选择避免新增可靠地址注册握手，但不是最紧凑的报头。完整48B地址复用使instance等信息重复携带，
部分注册字段、版本和静态预算也每条重复；不能声称107B每一字节都不能再省。
若将来压缩为“首次可靠登记＋后续短连接ID”，还要处理登记丢失/ACK、旧实例、复用和失败清理，是另一项设计变更。
本轮选择先保留已经验证的语义；没有为了性能擅自缩字段或加新握手。

8B OSU SHORT实例：UB3＋可靠DATA104＋SHORT header8＋应用8＝123B；设备inline上限128B。
应用13B时128B恰好inline，14B时129B改走非inline；这个边界有实际WR观察，不能只靠算式。

## 源码文件分别干什么，为什么拆开

| 文件组 | 主要内容 | 为什么放这里 |
|---|---|---|
| rm_urma_ep.c/h | UCT SHORT/BCOPY/历史RMA入口、WR提交、pending、flush、EP销毁 | 操作入口和EP级行为；可靠SEND调用reliable，不在每个入口复制协议 |
| rm_urma_iface.c/h | Jetty/JFR/JFC创建销毁、完成路由、目标缓存、进度和失败处理 | iface拥有共享硬件资源，负责统一调度和最后关闭 |
| rm_urma_addr.c/h | 地址/控制头的编码解码、大小端与边界校验 | 无硬件副作用，link与reliable共用，可独立做字节测试 |
| rm_urma_link.c/h | iface地址建链、逻辑peer与硬件target复用、iface_v2信用流控和状态 | 多个EP共享远端身份，不能都塞进单个EP私有状态 |
| rm_urma_reliable.c/h | PSN、重放、连续接收去重、累计ACK、定时重发及记录回收 | 可靠协议职责集中，ep/iface只负责调用和资源/完成接入 |

iface是本地交通站；EP是UCT给上层使用的逻辑出口；peer是该站到某个远端站的共享流状态。
多个EP指向同一个peer，peer借用iface管理的硬件target，本地多个EP借用同一个Jetty。没有创建新协议层或新硬件队列。
这种共享范围下若每个EP各从PSN1开始、接收却按远端iface判流，会产生序号冲突；可以另设计每EP流ID，
但那需要报文标识和反向关系管理。当前选peer流，PSN自然放peer。

RC目录是2个C＋2个H；UM是2个C＋4个H，还包括def/inl，不能说UM只有ep和iface四个文件。
UM已经把相关状态机集中在EP/iface里；RC软件层依赖底层可靠连接。RM还保留legacy_ep、iface_v2、reliable_v3和暂停的原生RMA路径，
所以文件数或总行数不是对等功能的比较。

addr/link在2026-10-27的iface建链阶段加入，reliable在2026-11-02的保序/重传阶段加入。
职责必须有人承担，但独立文件并非协议要求；合并回ep/iface也行，只会把那两个文件写大，不能当成逻辑减少。
本轮按“如无必要勿增实体”查的是重复实现、状态和资源，而不是文件名数量。

本次精简：8个既有产品文件增加107行、删除137行，净减30物理行，无新增产品文件、结构体、字段、池或配置。
