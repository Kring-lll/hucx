## 所选范围

共 40 个双节点 MPI 任务，最高每节点 4 个 rank，不跑满核：

- 原版 OSU 7.5.2 `osu_multi_lat --validation`：PPN1/2/4，尺寸
  8/3980/3981/3982/7937/7938/7939/16384/65536/1048576B，共30项。
  可靠模式 AM_BCOPY=3989；3981和7938为固定 eager 头布局计算值，
  不是通用 MPI 上限。有效配置、实际能力与逐 SEND 长度分别核验。
- 3个自编 MPI 正常任务：每个配对按
  8→3981→8→3982→64→7938→8→7939→117→65536→8→1048576→8
  反复两遍，然后反向重复。每 rank 各发送/接收26条，接收检查相同tag下的
  内容序号、消息/字节计数及完整剩余缓冲 guard。两阶段均做有界重复探测。
  结果在成功 Finalize 后按实际 rank/PID/nonce分别落盘，避免终端文本交错。
- AM切换6项：PPN1的16383/16384/16385/65536/1048576B，PPN4的65536B。
  固定阈值16KiB，原生RMA与AM_ZCOPY关闭，分进程REQ日志关联实际请求，
  证明阈值下eager、阈值上AM rendezvous；配置本身不当作路径证明。
- 软件注入1项：PPN1，8→65536→8两个方向。按固定UCP FIRST/MIDDLE
  头识别64KiB消息，重复第一个内部片，丢弃后一个内部片，并丢前两个ACK。
  每个真实应用PID必须有独立注入计数及生产重传post日志；双向各一个DATA丢弃，
  共两次DATA/四次ACK丢弃、两次重复译码。缺少触发证据就停止。

软件注入发生于成功硬件接收后、生产译码前，不是硬件网络丢包实验。
此处观测范围内无重复交付，不承诺任意延迟下完整去重证明。计时开启了校验、
观察器或诊断，不用作性能优势。完整C/D、故障设备恢复、event/wakeup等仍待验收。
READ/WRITE、MPI单边、原子、PPN192保持暂停。

## 运行与隔离

默认 `python3 NODE_ZIP` 只校验包并显示计划，不访问设备、不SSH。
`--preflight-only` 校验双端库/配置/能力/OSU/CPU、单进程帮助查询并编译探针；
不启动双节点MPI。`--run` 才顺序运行40项，遇到失败停止。

节点包从固定Git提交打包依赖，不修改旧 CASE/source/install。在已测CASE内创建
新的 `send_tools_fixed_*` 工具目录与 `send_integration_fixed_*` 结果目录。
本端编译一次后复制相同二进制到对端，复核SHA/依赖；不比较不同路径下带调试信息
的独立编译结果。OSU复用框架通过上下文同时绑定候选目录、提交、模块及配置检查，
返回时恢复原状态。配置支持4K/16K及100.00ms等等价显示，不跳过实际值检查。

单任务rank限时240秒，launcher额外20秒。清理复用已验证的nonce＋精确run目录
匹配与PID启动时间检查，只处理本轮进程；不执行节点级pkill或设备复位。
保留每任务trial.json、命令/配置、实际应用maps、原版OSU输出、WR摘要、
必要的完整UCX日志和总体results.json。大日志使用已有流式校验/哈希传输，
不裁剪后声称完整检查。

本地检查包含真实C探针的2/4/8进程CPU接口模拟、数据/远端guard故障拒绝、
实际dlopen注入器转发，以及原OSU接口模式/版本绑定测试。这些不是ARM/HMPI/URMA
节点验收。真正MPI编译与硬件通信结果只能由节点运行确认。
