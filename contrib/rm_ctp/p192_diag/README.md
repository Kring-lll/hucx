# PPN192单轮调用栈诊断（2026-10-28）

## 已有证据与本次范围

标准OSU两个用例已通过PPN160。原192 multi_lat首轮校验600秒超时：两端各192个进程Init后快照齐，未进入Finalize，没有8B结果行。
用户补充证据：启动时每rank绑1个CPU、无重叠；包装器启动至Init后快照约34秒。因此后续约560秒没有完成该轮，尚不清楚具体等待位置。启动绑核记录不等于应用全程调度证明。
node89有/usr/bin/gdb，node97没有。本包不安装任何软件，不改变产品/OSU二进制，不提高原600秒超时，不重跑32～160，不运行RC。

## 实现

复用已测OSU runner、启动器、库来源检查、参数生成、绑核和nonce清理；固定一轮RM PPN192 multi_lat校验，8B/1000次迭代/100次预热/600秒rank时限。
仅增加监督器：启动器运行约90/150秒时，检查随机nonce、准确结果目录、rank、父进程启动时间及实际OSU可执行文件后，在node89抽样rank0/96/189各抓一次GDB线程栈。
GDB每次最多12秒，采样结束后detach；异常退出后再次校验目标身份才向该OSU进程发SIGCONT，避免本轮进程遗留暂停状态。
node97只读取相同本轮标记的进程及阶段/实际主线程绑核信息，不依赖GDB、不调用远端未知程序。
两次采样后主动终止本轮自建launcher组，继续使用原有严格nonce+结果目录+启动时间检查清理rank。没有全局pkill/设备复位/对其他MPI任务的操作。
诊断会短暂停顿抽样进程，只作定位，不可把其耗时写回性能表。默认采样后主动停止不表示本轮又发生了600秒超时。
若原故障未重现并提前退出0，仍按原检查器读取数据/映射/退出证据；只记单轮诊断通过，不宣布完整PPN192验收。
